What changed from the earlier reference files

  • Configuration and local credentials are isolated by organization ID: aes-stage.ml.<OrgId>.json and aes-stage.ml.<OrgId>.credentials.json.
  • Numbered logout scenarios stop after the approved login page displays; they do not click browser Back or test direct protected routes. One separate standalone Organization User Browser Back workflow runs for each of 140462, 140463, and 140466—three validations total.
  • Scenario 15, Security → Manage User Access, is retired. Scenario 13 runs only for the exact standalone Organization 140462 mapping and produces two independent Manage Access outcomes; all other contexts omit it.
  • Campus User has seven scenarios: 3, 7, 14, 16, 17, 20, and 21.
  • Substitute Scenario 14 validates Available Jobs, Scheduled Jobs/Schedule, Past Jobs/History Jobs, and Non Work Days. An individual job is not required, and a valid zero-job state is acceptable.
  • Every potential FAIL receives a full 120-second observation/polling window. A future report is rejected when a FAIL does not record failureObservationSeconds: 120 and its timeout step. Transient overlays and missing page/account shells receive the same 120-second readiness window with one safe refresh after 60 seconds.
  • App Switcher validation is dynamic: test every displayed enabled application and return to Absence Management. Do not require a fixed inventory.
  • Every invocation uses a fresh isolated headed Chrome window and one continuous full-browser video including the address bar, with no blur, masking, dimming, overlays, annotations, or chapter cards.
  • Reports and archives are isolated under reports/full-suite/<OrgId>/; starting a run archives only that organization’s previous current report and ZIP.
  • The stable URL marker comes from the selected organization config. A mismatch is a separate WARNING when functional navigation still works.

Role-adapted Scenario 14

  • Organization User: Prefer an existing absence; otherwise use only a uniquely verified safe create → validate → cleanup lifecycle.
  • Campus User: Prefer an existing absence; create only when both safe creation and cleanup are exposed in the same Campus context.
  • Employee: Prefer an existing self-service absence; create only when the current identity can safely reopen and remove the exact record without substitute notification.

Canonical execution and reporting requirements

  1. Run readiness with the selected OrgId; execute only its enabledControllers in manifest order.
  2. Use one fresh isolated headed Chrome context and one dedicated 1280×720 browser window for the complete selected run.
  3. Record one continuous Chrome outer-window video, including tabs and the address bar. Capture measured account/workflow boundaries; never estimate or evenly divide video ranges.
  4. Capture a full-browser screenshot for every workflow and additional final evidence for FAIL, BLOCKED, NOT TESTED, and WARNING outcomes.
  5. Wait/poll 120 seconds before FAIL. For transient overlays or missing page/account shells, use the same 120-second readiness window with one safe refresh after 60 seconds; do not delay or reclassify genuine missing-data, permission, safety, or intentional data-gate outcomes.
  6. Continue through independent failures. Preserve role/context identity and repeat shared scenario IDs for every applicable context.
  7. Generate the master index.html, one self-contained role/login-combination folder, scenario pages, screenshots, measured timeline, one shared video, totals, reproduction steps, and portable ZIP.

Secure setup after clone or pull

  1. Choose the organization ID.
  2. Confirm config/aes-stage.ml.<OrgId>.json exists and contains the intended enabled controllers.
  3. Create the ignored local credential file:
PowerShell
Copy-Item .secrets/aes-stage.ml.<OrgId>.credentials.example.json .secrets/aes-stage.ml.<OrgId>.credentials.json
  1. Replace every required placeholder locally. Never commit the real credentials file.
  2. Run readiness:
PowerShell
powershell -ExecutionPolicy Bypass -File scripts/check-multi-user-run-readiness.ps1 -OrgId <OrgId>

Never put passwords, tokens, cookies, authorization data, sensitive redirect fragments, or personal test data in prompts, reports, screenshots, video filenames, or committed files.
